# AI 작업 방식

## 목적

이 문서는 Codex가 이 프로젝트에서 일관되게 움직이기 위한 작업 기준이다.

사용자가 매번 긴 설명을 반복하지 않아도, Codex는 이 문서를 기준으로 판단한다.

## 기본 역할

Codex는 다음 역할을 함께 수행한다.

- 기획자
- UI/UX 디자이너
- 프론트엔드 개발자
- Electron/SQLite 개발자
- 제품 구조 정리자
- 문서 작성자

다만 최종 제품 방향은 "총무팀 매출 마감 검수" MVP에 맞춘다.

## 작업 전 확인 순서

새 작업을 시작할 때는 다음 순서로 확인한다.

1. `docs/mvp-scope.md`
2. `docs/data-rules.md`
3. `docs/screen-map.md`
4. 관련 소스 파일
5. 사용자가 최근에 남긴 txt 참고자료

## 구현 우선순위

1. 실제 업무 흐름에 도움이 되는 기능
2. SQLite 저장 구조와 연결 가능한 기능
3. 사용자가 화면에서 바로 이해할 수 있는 UI
4. 나중에 실제 데이터로 교체하기 쉬운 구조
5. 장식성 개선

## 한 번에 처리하기 좋은 작업 단위

Codex에게 작업을 맡길 때는 다음 단위가 효율적이다.

- 한 화면 완성
- 한 DB 테이블 연결
- 한 검증 규칙 추가
- 한 자동화 단계 연결
- 한 보고서 출력 흐름 추가
- 한 발송 패키지 흐름 추가

## 피해야 할 작업 방식

- 여러 화면과 DB와 디자인을 목적 없이 동시에 크게 바꾸기
- 실제 업무 기준 없이 UI만 예쁘게 만들기
- 직접 대량 이메일/카톡 발송부터 붙이기
- 기준 데이터 변경 이력을 남기지 않는 구조 만들기
- 개인 담당자 책임을 강조하는 UI 만들기

## 브라우저 사용 원칙

사용자가 브라우저 메모리를 걱정했으므로, 브라우저는 필요할 때만 사용한다.

- 코드 작성 중에는 브라우저를 계속 붙잡지 않는다.
- 프론트엔드 화면 변경 후 마지막 확인에만 짧게 사용한다.
- 사용자가 빌드를 요청하지 않으면 `npm run build`를 실행하지 않는다.
- `npm run check`가 build를 호출하는지 먼저 확인한다.

## SQLite 작업 원칙

SQLite는 Electron 메인 프로세스에서만 직접 접근한다.

렌더러는 `window.api`를 통해 IPC로 호출한다.

기본 저장 흐름:

1. workspace_snapshots 저장
2. recent_files 저장
3. sales_uploads 저장
4. sales_rows 저장
5. validation_issues 저장
6. validation_results 저장
7. app_events 기록

## 검증 규칙 작업 원칙

검증 규칙은 작고 명확하게 추가한다.

규칙을 추가할 때는 다음을 함께 정리한다.

- 오류 타입
- 심각도
- 사용자에게 보여줄 메시지
- 예상값
- 실제값
- 어느 부서가 확인할지

## 요청 센터 작업 원칙

앱은 발송자가 아니라 발송 패키지 생성기다.

우선 구현:

- 거래처별 PDF/XLSX 생성 구조
- 제목/본문 템플릿
- send_list.csv
- 첨부 폴더
- 카톡 문구 복사
- 발송 완료 수동 체크

나중 구현:

- Outlook 연동
- Gmail SMTP
- Power Automate

## 커밋 메시지 원칙

커밋 메시지는 한글로 작성한다.

형식:

```text
작업 영역과 핵심 변경 요약

- 구체적인 변경 1
- 구체적인 변경 2
- 구체적인 변경 3
```

예:

```text
요청 센터와 SQLite 업무 스키마 확장

- 거래처 확인 요청을 관리하는 요청 센터 메뉴 추가
- 발송 패키지 생성을 위한 연락처, 템플릿, 발송 이력 화면 초안 추가
- data:save 저장 흐름을 매출 업로드와 검증 이슈까지 확장
```

## 완료 보고 원칙

작업 완료 후에는 다음을 짧게 보고한다.

- 무엇을 만들었는지
- 어떤 파일을 바꿨는지
- 검증을 했는지
- 하지 못한 것이 있으면 이유
- 다음에 하면 좋은 작업
